引言：从死循环到一条命令救场

我的联想拯救者 R7000P（Windows 11 25H2）开启安全启动后一选 Windows Boot Manager 就立刻弹回 BIOS，以为是 Secure Boot 证书链炸了，折腾了一轮：多次在 BIOS 里“重置为设定模式 + 恢复出厂设置”，保留数据重装系统，sfc/DISM/bcdboot 都试过，甚至从 U 盘的 Ventoy 启动也报 0x1A Security Violation。最后是在 WinPE 里用 bcdboot 重建 EFI 引导修好的。这篇按时间线把踩坑与线索记录下来，希望帮到同款机型遇到类似问题的朋友。

一、问题表现与初步排查

症状

  • 开启 Secure Boot 后：
    • 从硬盘选择 Windows Boot Manager → 过一会又回到启动选择界面（循环）。
    • 从 Ventoy U 盘启动 → 报错 Verification failed (0x1A) Security Violation（这与不少 Ventoy + Secure Boot 的案例一致） 1 2。

早期排查

  1. 临时关闭 Secure Boot → 系统能正常进入，证明不是硬盘/系统彻底损坏。
  2. 系统内修复：
    • sfc /scannow → 无异常。
    • DISM /Online /Cleanup-Image /RestoreHealth → 无异常。
    • bcdboot C:\Windows /l zh-cn → 不存在。

二、BIOS 侧：只有“重置为设定模式 / 恢复出厂设置 / 清除 AMD PSP Key”

我的这台 R7000P 为新版 BIOS（M3CN48WW），Security 页面下并没有“Key Management/密钥管理”子菜单，只能看到：

  • 清除 AMD PSP Key
  • 重置为设定模式（Reset to Setup Mode）
  • 恢复出厂设置（Restore Factory Keys）

我按联想文档/公告里的通用流程做过：

  1. Reset to Setup Mode → Yes
  2. Restore Factory Keys → Yes
  3. 确认 Platform Mode 回到 User Mode，Secure Boot 设为 Enabled → F10 保存并重启 3。

结果：问题依旧，硬盘和 Ventoy 都 0x1A。
联想的安全公告提到，部分受影响机型需要“Reset to Setup Mode + Restore Factory Keys”以清理测试密钥、恢复合法的 SB 密钥状态 3。但我的案例说明，单靠这两步并不总能修好。

关于“清除 AMD PSP Key”

  • AMD PSP 与 fTPM/Secure Boot 强关联，社区有用户反馈在 R 系列上关闭/清除 PSP 后出现无限重启，需要重新开启或刷 BIOS 救回 4。
  • 我没动这个选项，以免把问题从“卡启动”变成“直接砖机”。其实动了不过还好没发生什么事……

三、Win11 25H2 与 2023 证书的时间线背景

微软已在推进从“Windows UEFI CA 2011”到“Windows UEFI CA 2023”的证书更替，2011 证书将在 2026 年 6 月过期 5 6 7。部分 2026 年 2 月的累积更新将引导管理器改用 2023 证书签名，如果 UEFI 固件的 DB 数据库里没有 2023 证书，就会出现签名校验失败、启动被拦截的现象 8。

理论上，Windows Update 会尝试把 2023 证书写入 UEFI 的 DB；但很多 2015–2018 年前后出厂的 UEFI 实现（包括部分消费本）对“从 OS 动态更新密钥库”支持不完善，导致同步失败，引导文件已是 2023 签名，却少了对应的信任根证书 8。

结合我这台机子：

  • Secure Boot 开 → 硬盘引导与 Ventoy 均被 0x1A 拦截；
  • BIOS 又没提供 Key Management 界面让我手动 Append 2023 证书；
  • 官方 BIOS 最新停留在 M3CN48WW，未见 M3CN49WW 发布。

一度怀疑是“DB 里缺 2023 证书”导致的固件层信任链断裂。于是继续尝试各种路径，但这趟弯路却不是最终解。

四、尝试过的错误方向（后来证明不是根因）

  1. 在系统内用 Set-SecureBootUEFI 把 2023 证书写入 DB

    • 命令类似：Set-SecureBootUEFI -Name db -Content $certBytes -AppendWrite …
    • 结果报错 0xC000000D（STATUS_INVALID_PARAMETER）。
    • 微软文档说明 Set-SecureBootUEFI 需要 Format-SecureBootUEFI 打包后的格式化对象，且依赖固件是否支持该写入路径，直接传裸字节流会失败 6。我这台固件显然不支持这种写入。

  2. 试图在 BIOS 里通过 Key Management 导入 2023 证书

    • 现实情况：我的 R7000P 根本没有这个子菜单，这条路走不通。

  3. 寄希望于新版 BIOS（M3CN49WW）一揽子解决

    • 联想驱动页与多个镜像站都没有发布 M3CN49WW，当前最新仍为 M3CN48WW。联想公告文档里提到的最低 49 才包含 2023 证书，但实际点进链接跳转的还是 48 下载页面——还有反转，下载了安装以后在 ventage 里面看实际又是 49（）
      但无论如何，最新 BIOS 下重置设定模式和恢复出厂设置依旧无果。

  4. 以为 WinPE 能帮忙改 UEFI 的 DB/KEK

    • 实际上，WinPE 主要用于分区、引导修复、系统部署等；它并不能直接修改 UEFI 固件里的 Secure Boot 密钥库（PK/KEK/db/dbx），这套变量必须由固件侧写入或通过厂商提供的专用路径来更新 6。

五、Ventoy 的 0x1A：确认问题在“Secure Boot 拦截”，而不是 U 盘坏了

在 Secure Boot 开启时，从 Ventoy U 盘启动直接报：

  • Verification failed (0x1A) Security Violation

Ventoy 官方和社区都指出，这是 Secure Boot 不信任其引导文件所致。常规解法：

  • 在 0x1A 界面按 OK → 进入 MOK Management → Enroll key from disk → 选 ENROLL_THIS_KEY_IN_MOKMANAGER.cer → Continue → Yes → Reboot 9【t10](https://blog.csdn.net/jycjyc/article/details/152789052) 1 2。

这说明：

  • 只要 Secure Boot 开，Ventoy 的引导程序也会被拦截；
  • 这条 MOK 注册路径只把 Ventoy 自己的 MOK 公钥加入本机信任列表，并不会把“Windows UEFI CA 2023”等系统级证书写入 DB/KEK，因此救不了硬盘引导问题。

六、最终解决：WinPE 里用 bcdboot 重建 EFI 引导

最后问了 GPT，回到 glm 最开始给出的方案，用 bcdboot 解决。

绕开所有与证书、密钥相关的折腾后，最终是在 WinPE 里用 bcdboot 把 EFI 分区的引导文件重新写了一遍，问题就消失了。

大致步骤（以我的环境为例）：

  1. Ventory Enroll Key 以后得以正常启动 Ventory，从 WinPE U 盘启动（PE 要支持 UEFI）。
  2. 在 PE 的命令提示符里：
    挂载 EFI 分区
  1. 执行 bcdboot（关键参数）：
  • /l zh-cn：语言（可选，实际也没选）
  • /s S:：把引导文件写入 EFI 分区（这里挂载为 S:）
  • /f UEFI：指定固件类型为 UEFI

微软文档强调，bcdboot 可用来把关键启动文件（如 bootmgr.efi、BCD）复制到系统分区或 EFI 分区，并新建/修复 BCD 存储，这正是重建引导链的标准方法 11。

  1. 完成后重启解决

七、为什么最后是 bcdboot 而不是证书？

从现象和结果倒推，我这台 R7000P 的问题更像：

  • EFI 分区中的引导文件/BCD 存储状态与当前系统版本、分区布局或安全策略出现不匹配，导致 Secure Boot 校验失败；
  • bcdboot 重新写入引导文件与 BCD 后，引导链回到一个干净、一致的状态，Secure Boot 校验通过。

至于 2023 证书与 DB/KEK 的内容：

  • 我的固件里大概率已具备相应信任根（或至少没有到“完全缺失”的程度），只是 EFI 侧的引导文件/配置一度异常，造成安全校验不通过；
  • 因此，重建 EFI 引导就能把问题解决。

这也说明：

  • 并不是所有 0x1A 都一定是“固件 DB 缺 2023 证书”造成的；
  • EFI 引导文件/BCD 损坏或不一致，同样会在 Secure Boot 开启时表现为验证失败。

八、给同机/同症状的几点实用建议

  • 先确认关键信息：

    • BIOS 版本（我这台是 M3CN48WW）；
    • Security 下是否有“Key Management/密钥管理”子菜单（我这台没有）；
    • Secure Boot 关闭时能否正常进系统。

  • 关 Secure Boot 后进入系统，先做一轮轻量修复（如果有条件）：

    • sfc /scannow
    • DISM /Online /Cleanup-Image /RestoreHealth

  • 如果还不行，走 WinPE + bcdboot 重建引导（建议把 EFI 分区挂载为 S:，执行 bcdboot C:\Windows /l zh-cn /s S: /f UEFI）；这是“重建启动链”的标准方法 11。

  • BIOS 里可以尝试“Reset to Setup Mode + Restore Factory Keys”（联想公告的通用建议），但如果你的机型和我一样没有 Key Management，不要指望它解决一切 3。

  • 慎动“清除 AMD PSP Key”，社区已有 R 系列因此反复重启的反例，风险较大 4。

  • 关于 Ventoy 的 0x1A：

    • 这通常通过 Enroll key from disk / Enroll hash from disk 解决，只影响 Ventoy 自己能不能在 Secure Boot 下启动，不影响 Windows 的系统引导 9 10 1 2。

九、小结

  • 省流版：在 WinPE 里用 bcdboot 重建 EFI 引导（bcdboot C:\Windows /l zh-cn /s S: /f UEFI）修好了。
  • 早期我怀疑是 Secure Boot 的 2023 证书更替导致 DB 里缺证书、密钥链断裂，走了不少弯路；但最终修复方案却和证书无关，只是把 EFI 侧的引导文件与 BCD 重新写了一遍。
  • 希望这篇踩坑记录能给拯救者 R7000P（尤其是 M3CN48WW）遇到“Secure Boot 开启后回 BIOS / Ventoy 0x1A”的朋友提供一个可参考的排查路径与“最后的大招”：bcdboot。
